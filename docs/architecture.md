# Threadforge architecture

## Runtime boundaries

- Go owns the local CLI/service, SQLite trace/proposal/audit state, JSONL ingestion, MCP/OTLP endpoints, and project-file transactions.
- TypeScript adapter packages translate host-specific events and configuration into versioned Threadforge contracts. Adapters never write the Go database directly.
- Python packages provide AnyJev decisions and RRSI-style evolution selection/pre-screen through versioned JSON-over-stdio messages. They never open the Go database; absent domain rules return incomplete rather than a false clean result.
- Project facts, decisions, policies, and approved procedures are version-controlled project records. Raw traces, model prompts, user preferences, and credentials remain local.

## Procedure lifecycle

`selected evidence -> explicit local-model draft -> structural validation -> held-out evaluation -> human review -> approved project record -> scoped retrieval -> explicit supersession`

`threadforge memory learn` consumes at most 32 sanitized Beacon events, sends only bounded action/harness/severity/summary fields to the configured offline Hugging Face model over the Python stdio interface, and creates a draft in SQLite. Missing local inference or unsafe/invalid output yields no candidate. It does not approve or publish a procedure; evaluation and human review remain separate operations.

Failed, stale, conflicting, incomplete, or privacy-blocked records are not presented as current guidance. Retrieval is advisory and is not execution authorization.

## Procedure Graph v1

The graph is a directed, typed structure. Nodes represent triggers, states, actions, checks, or outputs. Edges represent `requires`, `enables`, `leads_to`, `branches_to`, `loops_to`, or `validates`; edge conditions are descriptive and are not interpreted as executable code. Cycles are allowed, but guidance traversal is bounded by hop and node limits.

An approval requires a passing held-out validation report and an identified human reviewer. The reviewer field is a local audit label until a team-share attestation binds it to a trusted signing key. Team publication requires a policy-authorized Ed25519 signer, an explicit privacy-review role and confirmation, and redacted evidence; local trace references are stripped before publication. See [authenticated team procedure publication](team-authorization.md).

`threadforge procedure export-skill` creates a separate immutable `.threadforge/skills/<id>/rev-NNNNNN/SKILL.md` projection. The command requires explicit privacy review, emits only approved graph instructions and applicability, omits evidence/validation/reviewer metadata, and fails on a conflicting existing revision. It is a portable file export, not host installation or prompt injection.

### Source freshness and retrieval

Procedure graphs may include exact `source_files` entries containing repository-relative paths and lowercase SHA-256 digests. `threadforge procedure fingerprint` hashes only explicitly named regular files, refuses credential-bearing paths, and limits each request to 500 files / 256 MiB total. When HTTP or MCP is configured with `--project-root`, the local service hashes the source files for matching approved procedures and ignores caller-supplied fingerprints; a mismatch marks the procedure stale and withholds it. Without a configured root, context callers may supply matching `path_fingerprints`; absent hashes or baselines make returned guidance `unverified` and the response `incomplete`. Neither state is presented as verified-current guidance. Host adapters do not yet collect fingerprints automatically.

Direct MCP `threadforge_procedure_get` and `threadforge_procedure_guide` apply the same comparison: stale sources suppress the graph/neighborhood, while missing fingerprints are surfaced as incomplete/unverified. When started with `--project-root`, the local stdio server hashes the graph's recorded files itself; without that root, the caller must obtain current digests locally. A matching digest is a continuity check, not held-out acceptance or execution authority.

The loopback service serves `/dashboard` and `/v1/dashboard`. The dashboard summarizes only a bounded 16 MiB tail of local JSONL and omits trace bodies and raw attributes. Its observed-runtime view reports event counts and last-seen timestamps from that bounded tail; it does not discover installed/configured runtimes or claim that an unseen harness is absent. When a project ID is selected, it shows procedure/task counts and at most eight recent task IDs, titles, statuses, requirements states, and next actions; task objectives, criteria, and summaries are not returned by the dashboard projection. The TypeScript SDK emitter in `adapters/src/emit.ts` validates the canonical event envelope and sends bounded batches only to loopback `POST /v1/events`; remote collectors and redirects are rejected. It is a reusable SDK transport, not evidence of any host-specific runtime capture support.

`threadforge security scan` compiles vendored Beacon CEL threat-rule contracts and evaluates events in stable timestamp/sequence order. It bounds local JSONL and custom rule corpora, marks malformed input incomplete, and emits only finding metadata rather than event bodies. Loopback `GET /v1/security/scan` and the dashboard's explicit scan button return aggregate counts by default; an explicit opt-in may return at most 100 bounded finding summaries without event IDs or content. Severity gates affect the CLI exit status only; no rule executes a command or mutates a host.

`threadforge mcp print-config` emits a generic stdio MCP server fragment in JSON or TOML for manual host-specific merging. It is deliberately non-mutating. Codex CLI also has an explicit project `.codex/config.toml` manager; the host still controls project trust, and live retrieval verification remains incomplete. Antigravity and Codex have partial observational hook adapters that emit no host decisions. Automatic config installers and host-hook adapters remain partial until each host's live contract and preservation tests pass.

When launched with `--project-root`, HTTP `POST /v2/context` and MCP context retrieval also read approved project-file facts, decisions, and policies. `POST /v1/context` remains a procedure-only compatibility response. V2 applies project ID, optional module/path scope, supersession links, conflict keys, token/item bounds, and strict file/hash/privacy validation. Project-memory v2 pins explicit repository-relative evidence sources at publish and re-fingerprints them locally at retrieval; stale or unavailable source-bound records are withheld, while legacy v1 records remain explicitly unverified. Missing scope is reported as incomplete; conflicting entries are withheld; corrupt or privacy-invalid project files yield `privacy_blocked`. The service does not create or approve project memory during retrieval.

## Storage

- Local SQLite stores procedure proposals/revisions, evaluation reports, AnyJev calibration candidates and immutable approval/rejection/retirement snapshots, migration receipts/staged records, and append-only audit trails. AnyJev artifact writes use CAS revisions; only a human-approved active artifact can be attached to an explicit `decision run` request, and artifact payloads remain local.
- Version-controlled `.threadforge/memory/records/<kind>/<id>/rev-NNNNNN.json` files store approved facts, decisions, and policies. Each publish requires an expected revision, human reason, and explicit privacy-review confirmation; immutable files are SHA-256 chained and contain only redacted evidence digests.
- Approved procedures can be explicitly copied from local SQLite into `.threadforge/procedures/<id>/rev-NNNNNN.json`. Each shared revision is an atomic graph-plus-attestation envelope; publication and every read verify an Ed25519 signature, out-of-band-pinned local trust policy, subject, project grant, role grant, exact graph digest/revision, and privacy review. Unsigned legacy shared files are withheld. V2 HTTP/MCP context can retrieve verified graphs from a checkout even when local SQLite is empty.
- `threadforge procedure export-skill` separately projects an approved graph to an immutable Markdown skill file under `.threadforge/skills/`. It requires explicit privacy review, is idempotent only when the existing revision has identical bytes, and never edits host configuration or installs/injects the artifact.
- `threadforge procedure supersede` uses a revision compare-and-swap to withdraw an approved procedure only when a different approved procedure exists in the same project; it records an append-only audit event. `procedure publish-supersession` writes a privacy-reviewed tombstone only after the replacement is already published. Retrieval prefers the newest revision across SQLite and project files, so an older published approval cannot revive locally superseded guidance. Superseded IDs cannot be republished; use a new ID for a new procedure.
- The migration CLI snapshots a bounded allowlist of legacy files into a private local directory, sanitizes and reconciles normalized records, and stages them as `local_pending_review`; Beacon events are contract-validated, and AnyJev model bundles are deterministically split into model/question-bound calibration candidates, adaptation state, and labeled observations. None are activated, approved, merged, or shared by migration.
- The migration framework is not cutover-ready. Cutover evidence v4 now requires a verified, path-redacted, per-format coverage ledger; selected-source round trips, format fixture completeness, populated Mancode/RRSI roots, rollback rehearsal, conflict review, and release-wide reconciliation remain required.

`threadforge cutover assess` is a read-only release gate. It hashes bounded, repository-relative evidence artifacts, recomputes held-out metrics from task/run data, and verifies evaluator signatures against a separately supplied out-of-repository trust policy. It blocks unless every feature/source migration row, cross-harness coverage, held-out domain evaluation, explicit cost/token budget, and required reviewer approval is present and passing. It never retires legacy tools or changes their repositories. The current implementation has no passing report; see [cutover requirements](cutover.md).

## Task and session continuity v1

Local SQLite stores versioned task state (`objective`, acceptance criteria, status, progress summary, next action) and session state (harness, completed work, handoff summary, next action). Compare-and-swap revisions prevent stale writers from overwriting newer context. Every task/session revision stores a snapshot and an append-only audit event; checkpoint, handoff, review, and verification entries are append-only and may reference a session. Review and verification entries require an explicit `passed`, `failed`, or `inconclusive` result, and evidence is represented only by SHA-256 digests.

New tasks have a versioned requirements state. Clarification questions are append-only, answers are immutable, and human finalization requires zero unanswered questions plus a reason. Finalized requirements must be explicitly reopened before revision. Any requirements change clears an existing plan confirmation; `governed_execution` confirmation requires finalized requirements. This readiness record does not grant tool or filesystem authority. Older stored tasks without the optional requirements object remain readable, but cannot newly confirm governed execution until they complete the requirements workflow.

For registered team projects, continuity mutations at the SQLite store boundary require an Ed25519 authorization bound to the exact action, project/resource, expected revision, entity payload, audit reason, and currently pinned trust policy. The verified subject replaces arbitrary actor labels; signed evidence and the canonical policy snapshot are persisted atomically with the revision or entry. `threadforge team audit verify` validates retained signatures and scope transitions; `team scope decommission|restore` provides the signed freeze/reactivation lifecycle. `team sync pull|push` uses a Git ref with remote compare-and-swap to exchange only signed, privacy-reviewed published procedure records; it does not transport task/session authority or SQLite data. Local recovery uses private SQLite snapshots and an explicit staged-copy activation that freezes current team scopes before enabling ordinary store access. Recovery stays local-only and does not synchronize code, branches, or worktrees; Mancode-compatible claims, handoffs, authority migration and recovery are not implemented.

The CLI exposes `task create|show|list|update|requirements|plan|record|entries|history` and `session start|show|list|update|history`. `task plan template` emits a deterministic scaffold prefilled only with the task objective and acceptance criteria; `plan revise` stores bounded Markdown and an optional validated repository-relative implementation scope, while `plan confirm` records an explicit `plan_only` or `governed_execution` choice. Plan changes and decisions increment the parent task revision, use compare-and-swap, and appear in task-history snapshots with distinct audit actions. A plan revision clears its previous decision. Confirmation cannot change plan content or scope, and `governed_execution` requires finalized requirements and a non-empty include boundary. This is a planning record, not a filesystem sandbox or tool authorization. The loopback service provides read-only `/v1/tasks` and `/v1/tasks/{id}` endpoints plus task-scoped session, entry, and revision-history reads; MCP exposes read-only task/session/history tools. Task continuity is local data: it is never part of `/v1/context` or `/v2/context`, and it is not automatically injected into a host prompt. A caller must explicitly request the task by project or task ID. All free text is size-bounded and credential-scanned; retrieved notes remain advisory and untrusted. See [the task plan schema](../schema/task-plan-v1.schema.json) and [requirements workflow](requirements.md).
