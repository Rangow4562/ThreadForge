# All-or-nothing legacy cutover gate

`pkg/cutover/requirements_test.go` parses the Beacon runtime matrix and the feature-parity product-area table, then requires their IDs to match the assessor's required-ID lists. The Mancode bootstrap targets are explicit ID rows in `docs/source-matrix.md` and are checked the same way. This prevents new documented scope from silently bypassing the cutover gate; it does not prove that a feature is complete or that attached evidence is authentic.

Threadforge must not replace, uninstall, or retire Beacon, Mancode, AnyJev, or RRSI before the complete acceptance scope passes. `threadforge cutover assess` is a read-only gate: it evaluates a report and its artifacts, prints readiness and blockers, and never changes any legacy repository, alias, installation, or backup.

The current report schema is [`cutover-evidence-v6.schema.json`](../schema/cutover-evidence-v6.schema.json); v1-v5 reports are not accepted by the current assessor. The assessor hard-requires every feature row (including the distinct `mancode.task-plans` and `anyjev.artifact-lifecycle` gates), all Beacon documented runtime sources and Mancode bootstrap targets, all four source migrations, cross-harness coverage of every source, and the Beacon/Mancode/AnyJev plus three RRSI evaluation domains. `pkg/cutover/requirements_test.go` parses the documented Beacon source matrix and feature-parity table and fails if a source/feature row is added or removed without updating its required-ID mapping; Mancode targets are listed as explicit requirement-ID rows in `docs/source-matrix.md` and checked by the same test. New documented sources or product areas must be added to the required-ID lists in `pkg/cutover/requirements.go` before release evidence can be accepted. This consistency test prevents scope drift; it does not prove that a mapped feature is complete or that attached evidence is authentic.

The newly tracked Beacon session-handoff feature row maps to the distinct required feature ID `beacon.session-handoff`; it is not covered by the existing Beacon capture or Mancode task-continuity rows.

The GitHub Copilot CLI memory-access row maps to the distinct required feature ID `beacon.adapter.github-copilot-cli-memory`; this host-specific MCP/SDK integration does not inherit the broad `beacon.memory` acceptance result, and explicit MCP transport does not prove automatic injection or efficacy.

The AnyJev serving-depth benchmark is separately required as `anyjev.serving-benchmark`; completing the general AnyJev decision row does not substitute for a real serving-depth baseline comparison and independent held-out evidence.

Before typed decoding, cutover rejects duplicate JSON object keys at any depth (including escape-equivalent spellings), unknown fields, malformed or trailing data, nesting deeper than 128 levels, and inputs exceeding 4,000,000 JSON tokens. This applies to the top-level report, evaluation trials, evaluator and migration-reviewer trust stores and attestations, migration backup verification, and migration format-coverage artifacts. Strict parsing removes ambiguous interpretations; it does not authenticate benchmark execution or make caller-supplied evidence trustworthy.

Every feature-parity table row maps to its own cutover feature ID. Exporter rows, DeepSeek Harness, and individual AnyJev study/cache rows must each carry separate evidence; `requirements_test.go` rejects sharing a requirement ID across different rows so one broad evidence claim cannot mask an unverified sub-capability.

Every evidence reference is repository-relative to `--evidence-root`; symlinks, traversal segments, non-regular files, digest mismatches, files over 128 MiB, or more than 10 GiB of distinct evidence are rejected. Evidence files are hashed during assessment. Each migration must include a `threadforge.migration-format-coverage.v1` artifact generated from a verified local snapshot by `threadforge migrate coverage --manifest <snapshot\\manifest.json>`. The artifact provides a fixed per-product format catalog, path-redacted per-format file-set commitments, per-format source/import/exclusion/rejection totals, snapshot bindings, and aggregate counts. The assessor checks the catalog is complete, all rows reconcile, the product/source/snapshot fingerprints match the migration row, and there are no unclassified, unsupported, unconverted, or rejected inputs. Migration records must also show interruption recovery and rollback rehearsal, report zero unresolved conflicts, and prove zero credential records were imported.

Each migration must also reference a `threadforge.migration-source-backup-verification.v1` artifact from `threadforge migrate backup-verify`. The assessor validates its schema, requires `status=verified`, and binds its product, source fingerprint, and snapshot digest to that migration row. The CLI re-inspects product-eligible source formats to catch additions/removals since snapshot, then scans the complete source and backup file trees, verifies relative paths, bytes, modes, independent-copy status, and snapshot-listed source hashes without returning paths or contents; `migrate apply` repeats this check before staging. This is a path-free consistency receipt, not proof of off-device durability, ACL equivalence, evaluator identity, or future backup retention. Retain source and backup and review the apply/rollback evidence separately.

Mancode cutover rows additionally require a `threadforge.mancode-source-set.v1` inventory. `threadforge migrate sources --root <project-root>` discovers the project root plus all workspace directories under the Git common directory's `mancode/workspaces` and `.mancode/runtime/non-git`; the output contains local paths and is an operator aid, not shareable evidence. Create one snapshot per listed root, then run `threadforge migrate source-set --root <project-root> --manifest <manifest>` once per snapshot. The source-set command rediscovers the root inventory, rejects missing/extra/duplicate or stale snapshots, detects cross-root duplicate normalized record keys, and emits only role IDs, fingerprints, counts, and a deterministic inventory digest. The cutover report keeps project coverage/backup evidence in the Mancode migration row and adds separate `sources[]` coverage, backup, interruption-recovery, and rollback evidence for every external workspace. The assessor reconciles every component to the inventory and aggregate counts, and blocks duplicate record keys. This closes evidence composition for the known local source layouts; it does not prove that a caller selected the authoritative source repository or that populated production roots have been reconciled.

For legacy Mancode plans lacking historical body/version commitments, a signed reviewer attestation can supplement—but never rewrite—the source-binding result. The reviewer workflow starts from a locally verified snapshot, requires the original source and independent backup to reconcile, regenerates coverage from the snapshot, and writes a new coverage artifact without overwriting. A trusted reviewer confirms the exact plan/metadata pairing and declared version after inspecting the source. The signature binds the product, workflow commitment, source and snapshot fingerprints, metadata/plan source-set commitments, declared version/defaulting, reviewer identity, and decision. The source ledger continues to say `plan_content_binding_verified=false`; approval is a separate current human claim. During assessment, pass `--trusted-migration-reviewers <external-reviewer-trust.json>` from outside the candidate repository and evidence root. The canonical reviewer-policy digest appears in assessment schema v3. Missing, invalid, mismatched, or replayed attestations still block. This mechanism resolves only that binding-specific gate; it does not establish Mancode plan semantics or full cutover readiness.

The assessor verifies signed evaluator attestations against an out-of-band trust policy supplied with `--trusted-evaluators <external-trust.json>`. The policy must be outside both the candidate repository and evidence root; its semantic SHA-256 is included in the `threadforge.cutover-assessment.v3` result. Keys are scoped to evaluator IDs and domains with explicit validity windows. Signatures bind the held-out split role, dataset digest, derived task-set digest, evaluator digest, legacy commit, candidate commit, and exact outcome-artifact digest. Without a valid policy and matching signature, evaluations block. This proves that a configured key signed those claims; it still does not prove the signer actually executed the named benchmark. Trust-key custody, evaluator runtime controls, dataset/split provenance, and benchmark outcomes require independent CI/release review. Unit-test fixtures use synthetic evidence only and are never cutover evidence. A `ready` result is a consistency and signature-verification signal, not proof of benchmark execution or release authorization.

Each evaluation must reference a SHA-256-bound [`cutover-evaluation-trials-v1`](../schema/cutover-evaluation-trials-v1.schema.json) artifact and signed [`cutover-evaluation-attestation-v1`](../schema/cutover-evaluation-attestation-v1.schema.json). It contains exactly eight baseline runs and four to eight candidate runs over the identical held-out task set (up to 10,000 tasks). Each row contains only task and failure-signature digests, success, measured USD cost, and token count; raw tasks, prompts, responses, paths, and failure text are not accepted. Run IDs, dataset identity, evaluator identity/version/digest, legacy version/commit, and all task digests are validated. The assessor derives a canonical task-set digest, success rates, repeated-failure rates, total costs, and total tokens from these rows and blocks any report scalar that does not match.

`threadforge cutover attest-evaluation` is an operator workflow for recording an evaluator's signed claim; it does not run a benchmark or establish independent execution. It requires `--confirm-evaluator-assertion`, a dedicated Ed25519 identity present in the out-of-band `--trusted-evaluators` policy, a clean candidate checkout matching `candidate_commit`, and a separate clean legacy checkout matching the selected domain's `legacy_commit`. It verifies the held-out trials artifact digest, recomputes all report metrics, checks the evaluator/domain/dataset/task-set bindings, signs those claims, and verifies the new signature against the supplied trust policy. The trust policy and private identity must be outside candidate, legacy, and evidence roots. The artifact path must be a new safe relative path under `--evidence-root`; the updated report is written to a new path and neither input is overwritten. Its result schema is [`cutover-evaluation-attestation-result-v1`](../schema/cutover-evaluation-attestation-result-v1.schema.json) and always says benchmark execution was not performed by the command, independent execution is unverified, execution is unauthorized, and cutover is not ready.

Create an evaluator key pair in a protected directory, have the independent trust-policy owner install the corresponding public key with the evaluator ID, domain scope, and validity window, then run the attestation command only after personally reviewing and vouching for the pinned evaluation:

```powershell
threadforge team identity generate --private-key $env:USERPROFILE\.threadforge-evaluator\private.json --public-key $env:USERPROFILE\.threadforge-evaluator\public.json
threadforge cutover attest-evaluation `
  --report .threadforge\cutover\report.json `
  --domain beacon `
  --evidence-root .threadforge\cutover\evidence `
  --candidate-root D:\checkouts\threadforge-pinned `
  --legacy-root D:\checkouts\beacon-pinned `
  --identity $env:USERPROFILE\.threadforge-evaluator\private.json `
  --trusted-evaluators $env:THREADFORGE_TRUSTED_EVALUATORS `
  --attestation-path attestations\beacon-2026-10-29.json `
  --output-report .threadforge\cutover\report-attested.json `
  --confirm-evaluator-assertion
```

The `attestations` directory must already exist and must not contain symlinks; choose a fresh attestation filename for every output. The candidate, legacy, and evidence roots must be separate and non-nested. A successful signature means only that a currently trusted key signed the bound claim. It is not a benchmark receipt, independent execution proof, statistical review, or release approval.

Runs are ordered. A repeated failure is the same task digest and failure-signature digest appearing after its first occurrence in that treatment's earlier runs. The baseline and candidate repeat-failure rates divide repeats by all task outcomes after each treatment's first run. The noise floor is the configured confidence quantile (0.95–0.99) of the absolute difference from a paired task bootstrap with independent run resampling. The legacy method identifier `paired_task_and_independent_run_bootstrap_null` preserves its original equal-sized resampling for reproducibility; new artifacts should use `paired_task_and_independent_run_bootstrap_null_v2`, which resamples the actual estimator sizes: eight baseline runs and four to eight candidate runs drawn from the baseline distribution, with the same resampled task sequence in both groups. Both methods record a uint32 seed and 100–10,000 resamples; `task_count * bootstrap_resamples` is bounded to 1,500,000. Local deterministic Monte Carlo regression tests ran 1,000 null replicates for each of two synthetic distributions at both candidate-run limits; false-positive rates ranged from 0.8% to 2.3%. With an injected 0.30 absolute per-task failure-probability reduction, detection was 86.2% at four candidate runs and 94.6% at eight, while preserving task success. These self-generated scenarios do not establish independent statistical validity or real held-out efficacy. Candidate USD-cost and token budgets compare per-run totals, so unequal run counts cannot make the candidate appear cheaper merely by running fewer trials. Candidate performance must reduce repeat failures by more than the derived noise floor, preserve or improve task success, and stay within the reported overhead limits. Release-manager, security-reviewer, and license-reviewer approvals are required with evidence.

Both v1 and v2 outputs from `threadforge evolution evaluate paired` are explicitly diagnostic (`cutover_evidence_eligible: false`): they compare caller-supplied rows, do not run the benchmark, verify artifact hashes, or confirm that the split is held out. V2 adds run-level resampling and an eight-baseline-run bootstrap null, but this is not an independently validated noise study. Do not submit either output as the held-out acceptance artifact. Cutover requires independently run and reconciled benchmark evidence.

Run the gate only after CI and acceptance artifacts have been assembled. The candidate commit must match `HEAD` in a clean Git worktree; `--repository-root` defaults to the current directory:

```powershell
threadforge cutover assess --report .threadforge/cutover/report.json --evidence-root .threadforge/cutover/evidence --trusted-evaluators $env:THREADFORGE_TRUSTED_EVALUATORS --trusted-migration-reviewers $env:THREADFORGE_MANCODE_REVIEWERS --repository-root .
```

Exit code `0` means the supplied evidence satisfies the coded gate; exit code `1` means blocked or invalid evidence; exit code `2` means the command invocation is invalid. The result is not itself authorization to delete legacy data: review the evidence and retain source repositories and verified backups through an independently recorded cutover decision.

The current implementation is not cutover-ready. Host-specific integrations, semantic migration coverage, cross-harness acceptance runs, held-out benchmark artifacts, and approvals are still missing. An empty or incomplete report correctly fails closed.
