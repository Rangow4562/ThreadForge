# RRSI selection and local history

`threadforge evolution domain-validate --file <domain-validation-request.json>` validates versioned domain-result envelopes through Python JSON-over-stdio operation `evolution.domain.validate`. The request and response contracts are `schema/evolution-domain-validation-request-v1.schema.json` and `schema/evolution-domain-validation-v1.schema.json`. Coding requires Terminal-Bench 2.1 and SWE-bench Verified; agentic workspace requires Harvey LAB evolve/held-out plus JobBench, GDPval, and APEX-Agents; engineering design requires EngDesign-Open, EngDesign v1, and Frontier-Eng. Unknown and cross-domain split identifiers are rejected rather than included in a `validated` report. Every registered split requires at least two baseline and two candidate runs, a dataset SHA-256, evaluator ID/version/SHA-256, and per-run result SHA-256. Metric counts/rates must reconcile for coding, workspace, and engineering-design shapes. Missing splits or evidence return `incomplete`; credential-bearing requests are blocked without echoing the input.

`threadforge evolution domain-verify --file <domain-verification-request.json>` adds local byte-integrity checking through Python JSON-over-stdio operation `evolution.domain.verify`. Its request, response, and normalized run-record contracts are `schema/evolution-domain-verification-request-v1.schema.json`, `schema/evolution-domain-verification-v1.schema.json`, and `schema/evolution-domain-run-evidence-v1.schema.json`. The request names an absolute `evidence_root`; all artifact references are POSIX-style relative paths below it. Dataset and evaluator files are SHA-256 streamed, while run files must be bounded JSON records binding `domain`, `split_id`, `role`, `run_id`, and allowlisted metrics. Limits are 384 artifact references, 1 GiB per file, 4 GiB aggregate, and 2 MiB per normalized run record. Symlink/reparse components, traversal, changing files, hash mismatches, and malformed run records fail closed. Credential-bearing requests or parsed run records are blocked without echo; dataset/evaluator bytes are only hashed and remain local. Paths and file contents are never returned. `artifact_hashes_verified` means only that every submitted reference matched its local bytes; `required_split_scope_complete` reports whether all registered splits were supplied. `split_identity_verified` and `benchmark_execution_performed` stay false: this command does not prove task membership, source authenticity, or that a benchmark actually ran. Its result is never cutover evidence and never authorizes execution.

The vendored RRSI evaluation primitive (`python/rrsi/evaluate.py`) now checks that every task has exactly the configured `k` trial rows and aligned reward, weight, and token arrays. Rewards must be finite in `[0,1]`, weights finite and positive, token counts finite/nonnegative or null, and missing counts bounded by the task's trial count. Persisted `EvalResult` data is accepted only when `n_expected`, missing count, weighted score, and token mean recompute from those per-task rows. Baseline, held-out, normal round, candidate, re-evaluation, `Domain.run()`, and domain smoke execution are blocked unless the strict boolean config field `benchmark_execution_opt_in` is explicitly true (default false); a disabled round refuses before analysis/model calls, Git worktrees, or evaluation artifacts. This closes the smoke path that could otherwise launch Docker or a billable model before the full-evaluation guard. These consistency checks do not authenticate benchmark execution, dataset provenance, or result origin; use the isolated Engineering runtime and signed cutover evidence for those separate claims.

Bundles stay outside the source tree; IDs are returned only to the local caller. A read-only smoke against the pinned RRSI checkout verified the 61-ID EngDesign-Open and EngDesign-v1 pair and the pinned test-surface relationship hash. This proves source inventory identity only—not benchmark execution, scoring, or held-out efficacy. The CLI bundle builders are implemented.

`threadforge evolution evaluate paired --file <paired-evaluation-request.json>` compares caller-supplied, task-aligned results through Python JSON-over-stdio. The v1 contracts (`schema/evolution-paired-evaluation-request-v1.schema.json` and `schema/evolution-paired-evaluation-v1.schema.json`, operation `evolution.evaluate.paired`) remain supported for compatibility; v1 uses at least four baseline and two candidate runs and its run-excluding noise estimate remains provisional. Inputs declare `split_role: held_out`, include SHA-256 references for the dataset, evaluator, both configs, and every run, and provide identical task-ID sets. Each task row contains `repeated_failures`, `success`, `cost`, and `tokens`; `cost_unit` must be consistent across both sides.

The additive v2 contracts are `schema/evolution-paired-evaluation-request-v2.schema.json` and `schema/evolution-paired-evaluation-v2.schema.json` (operation `evolution.evaluate.paired.v2`). Select v2 by setting the request's `schema_version` to `threadforge.evolution-paired-evaluation-request.v2`; the CLI dispatches to the matching operation and response contract. V2 requires eight baseline runs and at least four candidate runs (up to eight each), resamples paired task IDs and run IDs for all metric intervals, and estimates the repeat-noise reference by comparing independently resampled groups drawn from the baseline runs over the same resampled tasks. The seeded resampling work is bounded by `task_count * bootstrap_resamples <= 1,500,000`; the request still explicitly supplies confidence, resample count, and cost/token limits. Task IDs are not returned, and credential-bearing inputs are blocked.

Both versions compare supplied rows; neither runs a benchmark, verifies referenced artifacts, or independently proves that a split is held out. V1 omits run-level uncertainty. V2 includes task- and run-level bootstrap resampling and uses eight baseline runs, but its baseline-derived bootstrap null is still a diagnostic estimate, not an independently validated noise-calibration study. Hashes remain references only (`artifact_hashes_verified: false`). A `metric_gate_status: passed` means only that the stated diagnostic gates passed; every result remains `cutover_evidence_eligible: false`, `acceptance_status: not_evaluated`, `benchmark_execution_performed: false`, `human_approval_required: true`, and `execution_authorized: false`. Do not submit either output as the held-out artifact required by `threadforge cutover assess`. Executable domain benchmarks, independent artifact/split reconciliation, release-grade noise calibration, and actual cutover evaluation remain outstanding.

`threadforge evolution repair --file <repair-request.json>` runs a bounded local-only analyst → critic → proposer workflow. Request v2 carries source-committed inventories through every attempt; deterministic screening blocks a known task-ID match before any role inference, and a repaired candidate is re-screened with the same verified sets. Missing benchmark sources remain reported in the result and private SQLite history; they are not converted into a complete claim. For an unblocked candidate, the analyst emits only fixed risk categories and validation-gap labels, then the critic receives that bounded analysis as untrusted context and makes an advisory accept/reject assessment. On a critic rejection only, the proposer may suggest a revised candidate; it is screened, analyzed, and critiqued again. All roles use the same configured local Hugging Face backend with distinct instructions, not independent model votes. `max_repairs` defaults to 1 and is capped at 2, so there are at most three analyst and critic passes and two proposer passes (eight local model calls maximum). Analyst output is retained as categorical labels only; free-form analysis is discarded. If inference fails, output is invalid, or credentials appear, the run returns no candidate. Invalid, unsafe, unavailable, or rejected repairs return no candidate; only a locally accepted candidate is included in the result. No repair is applied, approved, evaluated, or authorized by this command. V1 and v2 request/result contracts are `schema/evolution-repair-request-v1.schema.json`, `schema/evolution-repair-v1.schema.json`, `schema/evolution-repair-request-v2.schema.json`, and `schema/evolution-repair-v2.schema.json`.

To retain a result and rejection/edit metadata in local SQLite, add all recording fields:

```powershell
threadforge evolution repair --file .\repair-request.json `
  --record-id rrsi-repair-001 --project-id my-project `
  --actor local-user --reason "retain local repair review history" --db .\threadforge.sqlite
```

The append-only snapshot stores attempt digests, summaries, target modes, edit metadata, analyst categories, verdict/reason codes, and an audit record. Rejected diffs are not copied into the attempt list; an accepted candidate remains local in the run snapshot. Inspect runs with `evolution repair-history --project-id <id>` and `evolution repair-show --id <run-id>`. Reusing a run ID with different content fails. This remains a bounded local loop, not a full RRSI implementation: dynamic task-specific rules, benchmark execution adapters, held-out evaluation, and independent-model review remain incomplete.

Selection is advisory. It does not edit a harness, launch a benchmark, approve a candidate, or authorize execution. A recorded selection stays `pending_human_review`; a later release decision still needs structural checks, held-out no-regression evidence, and explicit human review.

To preserve one round locally, supply all recording metadata:

```powershell
threadforge evolution select --file .\selection-request.json `
  --record-id rrsi-round-001 --project-id my-project `
  --domain rrsi-agentic-workspace --actor local-user `
  --reason "retain the measured round for review" --db .\threadforge.sqlite
```

`--domain` must be `rrsi-coding`, `rrsi-agentic-workspace`, or `rrsi-engineering-design`. Without `--record-id`, selection is read-only and the audit metadata flags are rejected. `evolution history --project-id <id>` lists compact summaries; `evolution show --id <round-id>` displays the local record and audit event.

The SQLite round snapshot retains the incumbent metrics, `delta`, `s_star`, effective `beta0`, `beta1`, `w_s`, `w_c`, and `w_n`, incumbent component counts, every candidate's measured/rejected/unmeasured state and selection rationale, declared edit metadata, and an optional bounded candidate diff. Diffs and decision details remain local in the private SQLite store; the workflow does not import raw traces or store benchmark task trajectories. Round, candidate, edit, and audit rows are append-only, and reads reconcile their child rows against a SHA-256-protected round snapshot. Reusing a round ID with different contents fails with a conflict.

These remain bounded building blocks, not the complete RRSI lifecycle. Threadforge implements a bounded analyst → critic → proposer repair workflow with edit/rejection history, inventory-aware screening, and human approval still required. Local inference uses one configured checkpoint; when remote inference is explicitly enabled, the roles share one configured Vertex model. Neither setup makes them independent votes. Dynamic task-specific leakage rules, executable benchmark adapters, independent noise calibration, and held-out evaluation remain incomplete. Legacy `rrsi` remains untouched. Vendored RRSI code and notices are tracked in `THIRD_PARTY.md`.

### Local JobBench inventory derivation

`threadforge evolution inventory jobbench --file <jobbench-inventory-request.json>` invokes `evolution.inventory.jobbench.derive` against a local `JobBench/job-bench` checkout. The checkout's `HEAD` must be the pinned commit `d43a66575635da0d3f6cb9a20976dc1a60f3ffc9`.
