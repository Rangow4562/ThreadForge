# Memory outcome feedback

Threadforge can store an explicit, local report connecting one approved memory revision or versioned task-resume context contract to a task result. This is a data-collection aid for later review—not proof that a host or model displayed, received, followed, or used the guidance, or that it caused the task result.

```powershell
threadforge memory feedback record `
  --project-root C:\work\repo `
  --project-id repo:example `
  --task-id task-123 `
  --target-kind procedure `
  --target-id build-recovery `
  --target-revision 2 `
  --exposure used `
  --utility helpful `
  --task-result passed `
  --harness codex-cli
```

`--target-kind` accepts `procedure`, `fact`, `decision`, `policy`, or `task_context`. For memory targets, the project/task must match and the named revision must be approved in the local SQLite or project-file store. For `task_context`, use `--target-id task-resume-context --target-revision 1` and the exact `--retrieval-receipt-id` returned by `threadforge_task_resume_context_with_receipt`; the receipt binds the task ID, snapshot's task revision, optional resolved session, and prepared/withheld status. An optional `--session-id` must match the receipt and belong to that task/project. A `used` report requires utility `helpful`, `neutral`, or `harmful`; `shown_not_used` requires `not_assessed`. Task results are `passed`, `failed`, or `inconclusive`.

For a failed task, an operator may additionally supply `--failure-signature-sha256 <64-lowercase-hex>`: SHA-256 of a locally normalized and redacted failure signature. Threadforge accepts only the digest, never failure text, stack traces, prompts, or task content. The caller is responsible for normalization and redaction before hashing; a digest is not proof that two failures share a cause. Ordinary memory feedback uses `threadforge.memory-feedback.v2`; task-context feedback uses v3, while v1 and v2 records remain readable and unchanged. The optional digest is rejected for passed or inconclusive tasks.

`threadforge_procedure_get`, `threadforge_procedure_guide`, `threadforge_project_memory_read`, and `threadforge_project_memory_read_v2` accept optional `task_id` and `session_id`. `threadforge_context_get` accepts the same opt-in fields and returns `retrieval_receipts`, one per exact procedure or project-memory revision included in its bounded result. Context receipts are stored atomically as one task-scoped batch; per-memory freshness is included in the context response. Procedure targets use `threadforge.memory-retrieval-receipt.v1`; project-memory targets use v2, which also records freshness and target-result status. Pass the matching receipt ID as `--retrieval-receipt-id` when recording feedback; if the receipt has a `session_id`, pass the same `--session-id`. The receipt records that the MCP handler prepared a result; it cannot verify transport delivery, host display, model exposure, interpretation, or use. Receipts that withheld guidance cannot be linked to feedback. Context results that withhold a target or resolve no revision produce no receipt for that target. Omitting `task_id` preserves prior MCP behavior and creates no receipt; `session_id` without `task_id` is rejected.

Automatic prompt-memory hooks also write local receipts when `--task-id` successfully resolves inside the configured project, or when `--discover-active-task` finds exactly one eligible task. These `threadforge.memory-retrieval-receipt.v3` records identify the host (`claude-code`, `codex-cli`, `gemini-cli`, `cursor`, `qwen-code`, `antigravity`, `opencode`, or `copilot-cli`) and use `observation_boundary=hook_response_prepared`. A receipt is recorded per returned procedure or project-memory revision; `guidance_included` is true only when the complete formatted item survives the final bounded hook context and the host response carries that context. The hook never places receipt IDs in host output. Use `threadforge memory feedback receipts --project-id <id> --task-id <id>` to inspect content-free IDs, then pass a matching ID with `memory feedback record --retrieval-receipt-id <id>`. For explicit session selection, also pass the same `--session-id`; unique-task discovery does not attach an inferred session. No task selection, failed/mismatched task resolution, or ambiguous discovery creates hook receipts. These records mean only that a local hook response was prepared—not that a host delivered it, a model saw it, or anyone used it.

For explicit MCP task continuity, call `threadforge_task_resume_context_with_receipt` instead of the read-only `threadforge_task_resume_context`. It returns the same v1 context nested in a `threadforge.task-resume-context-with-receipt.v1` response and appends one v4 local receipt. The target is the fixed contract `task-resume-context` revision 1; `task_revision` separately binds the exact task snapshot so feedback can be grouped across distinct tasks. A resolved session ID is included when one was selected. `session_selection_required` is recorded with `guidance_included=false` and cannot be linked to feedback. The ordinary tool remains unchanged and writes no receipt. These v4 records prove only that the MCP handler prepared the point-in-time snapshot; they do not prove delivery, model exposure, interpretation, use, or efficacy.

The CLI generates a random event ID and appends the typed report to private SQLite schema version 14. Feedback and retrieval-receipt tables are append-only and each is capped at 100,000 records per project. `memory feedback list --project-id <id>` and `memory feedback receipts --project-id <id> --task-id <id>` return bounded pages (default 50, maximum 500); receipts v2 includes task-context receipt v4. `memory feedback summary --project-id <id> [--max-records 10000]` returns v3 count groups by target revision, harness, exposure, utility, and task result, plus the count linked to a retrieval receipt. Each group reports both `count` (feedback records) and `distinct_task_count`; repeated reports for one task therefore do not appear to be evidence from multiple tasks. Task IDs are used only for local aggregation and are not included in the summary. A summary is explicitly `truncated` when its bound omits records. Prior v1/v2 summary schemas remain available for existing artifacts.

`memory feedback repeats --project-id <id> [--max-records 10000]` groups failed v2/v3 records that include a failure-signature digest. Groups are separated by target contract/revision, harness, exposure, utility, and digest; task-context feedback uses the fixed `task-resume-context` contract target so repeated failures can be compared across tasks. `feedback_count` counts reports, `distinct_task_count` counts unique local task IDs, and `repeated_after_first_task_count` is the number of distinct tasks beyond the first; task IDs are never returned. Duplicate reports on one task do not inflate the repeated-task count. The result is a bounded, local, descriptive summary—not independent evaluation, causal attribution, or cutover evidence. Its `evidence_class`, `cutover_evidence_eligible`, and `execution_authorized` fields remain `self_reported`, `false`, and `false`.

Stored feedback fields are limited to project/task/session identifiers, an optional receipt ID, target kind/ID/revision, exposure and utility labels, task-result label, harness, reporter label, and timestamp. Receipts contain only identifiers, contract/task revisions, retrieval tool, host where applicable, freshness, result status where applicable, guidance-inclusion status, observation boundary, and timestamp. No task text, memory body, prompt, trace, file path, model output, or free-form rationale is accepted. Feedback and receipts stay in the local SQLite store and are not included in team procedure publication or sync. They do not alter retrieval ranking, memory approval, procedure status, or execution permissions.

Every record and summary sets `evidence_class=self_reported`, `cutover_evidence_eligible=false`, and `execution_authorized=false`. Counts are descriptive only. Independent held-out evaluation, authenticated evaluator execution, and measured cross-harness task outcomes remain required for efficacy or cutover claims.
