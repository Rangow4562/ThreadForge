# Legacy migration: current contract and gaps

Migration is deliberately a review workflow, not an automatic cutover. It never imports credentials, never marks imported knowledge approved, and never mutates the source tree. It currently creates private local snapshots of normalized JSON records, then stages those records in SQLite with scope `local_pending_review`.

## Command sequence

```powershell
threadforge migrate inspect --product <beacon|mancode|anyjev|rrsi> --root <legacy-data-root>
threadforge migrate snapshot --product <product> --root <legacy-data-root>
threadforge migrate backup-verify --manifest <THREADFORGE_HOME>/migrations/snapshots/<product>/<fingerprint>/manifest.json --backup-root <independent-retained-copy>
threadforge migrate coverage --manifest <THREADFORGE_HOME>/migrations/snapshots/<product>/<fingerprint>/manifest.json
threadforge migrate apply --manifest <THREADFORGE_HOME>/migrations/snapshots/<product>/<fingerprint>/manifest.json --backup-root <independent-retained-copy> [--progress-stderr]
threadforge migrate verify --manifest <THREADFORGE_HOME>/migrations/snapshots/<product>/<fingerprint>/manifest.json
threadforge migrate records --id <migration-id>
threadforge migrate rollback --id <migration-id> --reason "reviewed rollback"
threadforge migrate verify --manifest <THREADFORGE_HOME>/migrations/snapshots/<product>/<fingerprint>/manifest.json --expect rolled_back
```

`migrate coverage` accepts only a manifest inside Threadforge's private local snapshot directory. It verifies the snapshot through the normal manifest loader, then emits `threadforge.migration-format-coverage.v1`. The report contains the fixed product-specific format catalog (including zero-count families), SHA-256 commitments for each format's source-file set, source/snapshot hashes, and reconciled file/record totals. Raw source paths and the local source root are not emitted. `unclassified`, unsupported, rejected, and known-but-unconverted inputs remain separately visible; the cutover assessor blocks any of them rather than counting generic JSON staging as semantic migration. The per-format snapshot digest is SHA-256 over sorted path-redacted source/snapshot commitments, not a digest of the serialized migration manifest.

`inspect` reports eligible files and blocked/rejected records. Parser failures use fixed issue codes (`unsupported_source_format` or `source_validation_failed`); raw parser errors are never copied into the manifest. `snapshot` hashes the source before and during capture, writes sanitized normalized records under the local Threadforge data directory with owner-only permissions, and verifies the manifest and record digests. `apply` accepts only a verified snapshot inside the active Threadforge data directory; it does not read credentials or re-open the legacy source. Reapplying the same verified migration is idempotent. `rollback` removes staged records but retains the snapshot and audit history.

`verify` independently reconciles the verified snapshot with the SQLite receipt and staged rows, comparing IDs, types, source paths, local-review scope, payload bytes, hashes, and exclusion counts. Use `--expect rolled_back` after rollback to confirm the snapshot remains valid and no staged rows remain. The command emits only counts and generic mismatch codes, never record payloads, and its `cutover_authorized` field is always false. Apply uses a single SQLite transaction; an interrupted transaction is recovered by SQLite as either fully committed (then verifiable/idempotent) or absent (then safely reapplied from the retained snapshot). The opt-in `--progress-stderr` stream reports only staged/total counts, emitted while the transaction is still open; standard output remains the final JSON result. Store-level and CLI-level subprocess tests kill an importer after a synthetic record has been staged but before commit, then verify that reopening leaves no partial records or receipt and that retry succeeds.

`backup-verify` requires the snapshot manifest and an independent backup directory containing a full copy of the manifest's source root. It compares sorted relative file names, regular-file bytes, permission bits, file counts, and aggregate bytes; rejects overlapping roots, symbolic links/reparse points, special files, oversized trees, and files hard-linked between source and backup; re-runs the product-specific migration inventory to detect eligible source additions/removals since snapshot; and checks that snapshot-listed files still match their captured source hashes. It reads each tree twice and emits only a path-free `threadforge.migration-source-backup-verification.v1` receipt with source/snapshot bindings and tree digests. Bounds are 100,000 total tree entries, 10,000 files, 32 MiB/file, and 1 GiB/tree. A mismatch returns a receipt with `status=mismatch` and exit code 1. `migrate apply` requires `--backup-root` and repeats the comparison immediately before opening the migration transaction; it refuses a mismatch. The apply receipt includes the successful backup-verification report. This checks file content/paths/modes at verification time; it does not verify ACLs, alternate data streams, backup-medium durability, or future retention. Keep both original and backup until separate rollback and cutover reviews pass.

### Mancode local team-ref import

Mancode projects configured with `transport.mode="git-ref"` require an explicit opt-in for migration because the worktree alone is not the complete team source:

```powershell
threadforge migrate inspect --product mancode --root <project-root> --include-mancode-git-ref
threadforge migrate snapshot --product mancode --root <project-root> --include-mancode-git-ref
```

The importer reads only the already-local `refs/mancode/team` commit; it does not fetch, update refs, or contact a remote. The project root must be the root of a self-contained Git worktree (not a linked worktree or repository backed by object alternates), and the ref manifest must be a single root `manifest.json` blob no larger than 1 MB, bound to the project's configured workspace. Snapshots retain normalized review-only summaries, not the raw team manifest. Actor identities and receipt digest values are omitted. Supported task bundles are bounded to 16 artifacts and 256,000 serialized bytes per artifact; the importer verifies exact v1 fields, canonical content/bundle/aggregate digests, task and ownership binding, and Mancode v3 workflow-ledger consistency before importing typed workflow artifacts. Any malformed, conflicting, incomplete, credential-bearing, explicitly excluded, or privacy-sensitive bundle is rejected as a whole. The `threadforge.mancode-git-ref-task-bundle.v1` summary omits task identity and code reference; artifacts remain local pending review and never authorize execution. Schema-v2 privacy snapshots reuse the strict policy/exclusions converters and are imported only when the normalized policy digest, workspace, exclusions revision, and exclusions digest agree. Explicit entity-digest exclusions are checked against imported team entities, bundle code references, and artifact contents. When the source policy is enabled, its configured Mancode `mancode-sensitive-text:1` rules are reimplemented as a fail-closed import-time rejection scan over actor profiles, claims, handoffs, task-bundle code references, and artifact contents. Scans are bounded to 100,000 JSON nodes, 1 MiB per string, 4,096 findings, and 500 ms per string; invalid, oversized, or incomplete scans reject the affected entity. These rule IDs are not activated as Threadforge runtime policy: imported policy/exclusions remain historical only and never authorize execution. Valid authority freezes and tombstones now produce identity-reduced `threadforge.mancode-git-ref-authority-transition.v1` review records containing successor mode/epoch and event time only; operation and workspace references are omitted, and the records never change Threadforge authority. Malformed or inconsistent transitions remain rejected, and any rejection blocks cutover. See the [task-bundle](../schema/mancode-git-ref-task-bundle-v1.schema.json) and [authority-transition](../schema/mancode-git-ref-authority-transition-v1.schema.json) schemas. For `backup-verify` and `apply`, the independent retained copy must include the Git metadata and the same local team ref so the source binding can be revalidated. No populated Mancode state/ref was supplied, so this fixture-backed support is not actual-source reconciliation or cutover acceptance.

Limits are 10,000 eligible files, 32 MiB per source file, 1 GiB total source bytes, 100,000 decoded records, and 1 GiB of normalized snapshot records. Unsupported or malformed files are reported rather than guessed. Imported entries are not exposed as approved retrieval context.

For an actual-source CLI round trip, `internal/cli/migration_source_readback_test.go::TestConfiguredMigrationSourceReadback` accepts optional `THREADFORGE_BEACON_SOURCE`, `THREADFORGE_MANCODE_SOURCE`, `THREADFORGE_ANYJEV_SOURCE`, and `THREADFORGE_RRSI_SOURCE` directories. It runs inspect, snapshot, apply, idempotent reapply, and record-by-record verify using only `t.TempDir()` for Threadforge state; it checks the source fingerprint remains unchanged, requires all scanned files to be supported and records unrejected, and requires `cutover_authorized=false`. Credential-bearing paths are counted as excluded, not copied. If a configured root contains no eligible records, the test fails rather than treating an empty scan as acceptance evidence. Example in PowerShell:

```powershell

```

The test is skipped when no source variables are configured and leaves no snapshot or database behind. A passing source-specific round trip validates only that checkout and allowlist; it is not full cross-product migration or cutover approval.

## Current source allowlist

### Beacon Codex hook settings

Codex user/project `hooks.json` files are eligible only at `.codex/hooks.json` or when the selected source root itself is `.codex`. The strict `threadforge.beacon-harness-config.v1` projection records only `SessionStart` and legacy `Stop` event names whose nested command contains the exact Beacon `--platform codex` marker. It drops command text, matchers, secrets, environment, paths, MCP settings, and unrelated fields; records remain local pending review and never authorize execution. The pinned Beacon installer currently uses `SessionStart` for session context; `Stop` is accepted only as historical Beacon-owned config evidence, not as an active behavior claim.

Codex user/project `config.toml` files are eligible only at `.codex/config.toml` or when the selected source root itself is `.codex`. Strict TOML decoding emits `threadforge.beacon-codex-otel-config.v1` only for recognized OTLP log or trace exporter tables. It keeps the `dev`/`ci` environment label when known, the `log_user_prompt` boolean, exporter names, and endpoint locality (`loopback`, `non_loopback`, `not_configured`, or `unknown`); raw endpoints, headers, credentials, paths, and unrelated Codex settings are omitted. These are local pending-review records, not instructions to activate or forward telemetry.

### Beacon Gemini telemetry settings

Gemini `settings.json` is eligible only under `.gemini/settings.json` or when the selected source root itself is `.gemini`, and only when its telemetry block matches Beacon's local OTLP contract (`target=local`, loopback endpoint, `otlpProtocol=grpc`, and `useCollector=true`). `threadforge.beacon-gemini-otel-config.v1` retains only those fixed local-collector facts, optional `enabled`/`logPrompts`/`traces` booleans, and whether an `outfile` is configured. Raw endpoints, outfile paths, credentials, and unrelated Gemini settings are omitted. Beacon's pinned installer writes user-level settings; project settings and environment variables may override those settings, so the projection is review evidence, not proof of effective host configuration.

### Beacon Antigravity hook settings

Antigravity hook files are eligible only at `.gemini/config/hooks.json` or `.agents/hooks.json`, including when the matching directory is the selected source root. The importer reads only Beacon's top-level `beacon-endpoint` block and retains the six documented event names (`PreInvocation`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostInvocation`, `Stop`) that contain a matching `--platform antigravity` command. Other top-level hook owners and unmatched events are ignored. The shared `threadforge.beacon-harness-config.v1` record omits commands, matchers, credentials, paths, and unrelated settings; it remains human-review-required and non-authorizing.

### Beacon OpenHands hook settings

OpenHands `hooks.json` is eligible under `.openhands/hooks.json`, when the selected source root itself is `.openhands`, or directly under an explicitly selected custom persistence root (including `OH_PERSISTENCE_DIR`). For a custom root, at least one event must contain Beacon's exact `--platform openhands` command marker; arbitrary root-level hook files without that marker are rejected. The importer accepts Beacon's documented direct event map and legacy `{"hooks": ...}` wrapper, with either snake_case or PascalCase spellings for the six events. Duplicate spellings and unknown direct event keys are rejected to match OpenHands' fail-closed file contract. Only event names whose nested command contains the Beacon marker are retained; commands, matchers, credentials, paths, and wrapper siblings are omitted. The output is the shared `threadforge.beacon-harness-config.v1` local-review projection, never authorization.

### Beacon Kiro hook settings

Kiro's Beacon-owned `beacon-endpoint.json` is eligible under user/project `.kiro/hooks/`, when the selected root is `.kiro` or `.kiro/hooks`, and under an explicitly selected custom `KIRO_HOME` root. Custom roots require a matching `--platform kiro` command in the owned file. The importer accepts only `version="v1"`, a `hooks` array, unique documented Beacon triggers (`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`), command actions, boolean `enabled` values, and optional integer timeouts from 1 through 600 seconds. Non-Beacon hooks, malformed shapes, unknown root fields, and duplicate triggers are rejected. Only enabled matching event names are retained in `threadforge.beacon-harness-config.v1`; commands, names, descriptions, timeout values, credentials, environment, and paths are omitted. Imported configuration remains local pending review and cannot enable hooks.

### Beacon Kimi Code hook configuration

Kimi Code's user-level `config.toml` is eligible at `.kimi-code/config.toml`, when `.kimi-code` is the selected source root, or as `config.toml` under an explicitly selected custom `KIMI_CODE_HOME`. Custom roots require at least one `[[hooks]]` entry with Beacon's `--platform kimi` marker. The TOML decoder reads the full source in memory, but the projection retains only the 13 pinned Beacon event names from matching command entries; user hooks are ignored. Invalid Beacon event names, duplicate Beacon event registrations, malformed hook arrays, or out-of-range Beacon timeout values fail closed. API keys, providers, model catalog entries, commands, matchers, paths, and unrelated settings are never written to the migration snapshot. The shared hook contract records `source_format="toml"`, requires review, and never authorizes execution. Kimi Code has no project config path; per-project isolation uses a separately selected `KIMI_CODE_HOME` root.

### Beacon Muse Code managed hooks

Muse Code uses two user-level files below `~/.config/muse/`, or below `$XDG_CONFIG_HOME/muse/`: `beacon-endpoint-hooks.json` and `settings.json`. The importer stages them separately. The owned hooks file must carry Beacon's `beacon-managed-muse-hooks:v1` marker and its documented nested event/group/handler shape; only the ten allowlisted event names with `--platform muse` commands are retained. `settings.json` yields only whether `managed_hooks_path` is present and whether its basename matches `beacon-endpoint-hooks.json`; its path and all other settings are omitted. The settings-pointer record always sets `effective_registration_verified=false`: these two staged records are human-review evidence, not a cross-file runtime check or authorization. Project `.muse/hooks.json` is deliberately excluded because Beacon's pinned documentation says the shipping Muse build ignores it.

### AnyJev per-question head-study results

JSON files at `bench/results_heads/<YYYY-MM-DD>/*.typed.json` are normalized as `threadforge.anyjev-head-study-result.v1` only when their strict producer shape, path/date binding, exact baseline/head method matrices, solver-specific parameters, and pooled counts reconcile. The projection retains bounded aggregate and per-question accuracy, ECE, Brier, NLL, flip, sample-count, and head-selection metadata; model and question identifiers are hashed, while timestamps, seeds, environment details, raw predictions, and source paths are omitted. Accuracy, Brier, NLL, and flip reconcile from per-question weighted values; ECE is range-checked but is not recomputed from question-level ECE because it is non-linear. Imported results remain local, human-review-required historical evidence and never authorize execution or establish benchmark/cutover acceptance.

### Mancode pre-V3 workflow status bindings

The path-redacted `threadforge.mancode-legacy-workflow-binding.v1` check records whether optional metadata `requirementsStatus` and `verificationStatus` fields exist and, when present, compares them with normalized requirements readiness and the verification ledger's derived source status. A mismatch is a `conflicting` review result; absent metadata fields remain compatible and do not block an otherwise complete binding. These new booleans are optional and omitted when false so existing v1 manifests retain their serialized shape and source fingerprints. The checks remain local review evidence, require human review, and never authorize execution. Plan-body/version binding is still intentionally unverified.

## Actual-source reconciliation gaps and incomplete migration; no cutover authorization

The entries below distinguish code support from migration acceptance. Some listed formats have strict, fixture-tested converters, but have not been reconciled against a populated source-state inventory; other formats or producer variants still lack complete converters. A converter or synthetic lifecycle test is not evidence that a user's data was migrated. ### Mancode claim and handoff authority (not migrated)
