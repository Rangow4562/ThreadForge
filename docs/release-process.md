# Release-candidate build process

Threadforge does not publish a GitHub Release automatically. A stable `vMAJOR.MINOR.PATCH` tag starts the release-candidate jobs in `threadforge-tests.yml`, but only after the complete twelve-cell OS/Python test matrix and the Elasticsearch synthetic-ingestion job succeed. The tagged commit must be reachable from `main`. To exercise the release pipeline without creating a tag, manually run the workflow from `main` with `release_version` set to a stable `MAJOR.MINOR.PATCH`; this produces a rehearsal candidate tied to that tested `main` commit, not a tag-sourced production release.

The build creates the currently supported CLI artifacts and requires a separate twelve-cell Python evidence matrix (Linux, Windows, and macOS on Python 3.11, 3.12, 3.13, and 3.14) to succeed before candidate assembly:

- `threadforge_VERSION_linux_amd64.tar.gz`
- `threadforge_VERSION_darwin_amd64.tar.gz`
- `threadforge_VERSION_darwin_arm64.tar.gz`
- `threadforge_VERSION_windows_amd64.zip`

The version command is linked to the tag version. Each platform archive contains exactly one CLI binary plus the root `LICENSE`, `NOTICE`, `THIRD_PARTY.md`, and the matching target-specific Go license archive as `THIRD_PARTY_LICENSES.tar.gz`. The nested archive contains the bounded `go-licenses` report, evidence manifest, and discovered upstream license/notice texts. Outer archives normalize timestamps, ownership, member names, and metadata where the format permits; the Windows ZIP uses stored entries for byte-stable packaging. The same target-specific `threadforge_VERSION_GOOS_GOARCH.go-licenses.tar.gz` is also retained as a separate, independently attested candidate payload. The Go evidence uses pinned `go-licenses` v2.0.1 for `./cmd/threadforge` under that target's `GOOS`/`GOARCH`; unknown license expressions fail the candidate. The bundle records the source commit, scanner binary hash, notice-file hashes, unknown source-URL count, and native-code inspection warnings. These scanner classifications are unreviewed; the bundle sets `release_clearance=false` and is not legal approval.

For Python, the workflow installs all seven locked extras declared in `python/pyproject.toml` (`test`, `decisions`, `hf`, `serving`, `typed-data`, `evolution`, and `workspace`) on each of twelve OS/Python profiles and runs the complete Python suite with those extras enabled, then emits one `threadforge_VERSION_python_OS_pyPYTHON.license-evidence.tar.gz` archive per profile. New archives use `threadforge.python-license-evidence.v2`, which binds LF-normalized `uv.lock` and project-file hashes; v1 remains available for older raw-byte hashes. The archive records installed package metadata and safe license fields, and retains bounded license/notice files with per-file hashes. Collector-source and v2 input-manifest SHA-256 values normalize CRLF to LF so identical committed content hashes consistently across Windows and Unix checkouts. Installed packages not represented in `uv.lock`, unsafe paths, and oversized evidence fail the job. The archives are deterministic and individually provenance-attested. They remain unreviewed evidence (`release_clearance=false`), and do not cover the Engineering container/runtime or benchmark dataset/evaluator terms. See the [license audit](license-audit.md) for remaining scope and legal-review gaps.

If Syft installation or the first SBOM generation attempt fails, the pinned action is retried once; a second failure stops the candidate before attestation or upload. GitHub creates build-provenance attestations for each archive, SBOM, and Go/Python license-evidence bundle, a distinct SPDX SBOM attestation binding each binary archive to its SBOM, and a build-provenance attestation for the combined `checksums.txt`. Candidate assembly requires exactly 24 versioned payloads (4 CLI archives, 4 SPDX SBOMs, 4 Go evidence archives, and 12 Python evidence archives). All payloads are checksummed in the combined candidate bundle. The workflow uploads these files as a 14-day Actions artifact and has no `contents: write` permission, so it cannot publish or edit a public release.

Before attestation, `scripts/verify_release_sbom.py` reconciles each SPDX package set to that exact binary's `go version -m` output. It requires every embedded Go module, checks non-replaced module versions and the Go standard-library version, and rejects unexplained SBOM packages. Its JSON summary counts package license declarations/conclusions that remain unasserted and always sets `license_review_required=true` and `release_clearance=false`. This verifies Go-binary component coverage only; it does not classify licenses, review redistribution terms, cover Python/container runtime dependencies, or grant legal approval. Those release blockers remain tracked in [the dependency and license audit](license-audit.md).

After downloading the candidate artifact, verify the complete bundle with the repository verifier. It checks the exact 24-payload inventory, all payload checksums, archive member safety/layout, embedded-versus-separate Go license evidence, Go/Python evidence manifest bindings, 25 SLSA provenance attestations, and four archive-to-SPDX attestations. GitHub CLI must be authenticated and able to read the repository's attestations. Use the exact source commit and full ref recorded by the candidate workflow:

```bash
python scripts/verify_release_candidate.py \
  --bundle-dir ./threadforge-candidate \
  --version VERSION \
  --source-commit FULL_SOURCE_COMMIT_SHA \
  --source-ref refs/tags/vVERSION
```

For a `workflow_dispatch` rehearsal from the `main` branch, pass `--source-ref refs/heads/main`; for a tag-triggered candidate, pass its exact `refs/tags/vVERSION` ref. The verifier performs GitHub API lookups for each attestation and may take several minutes. Its success output proves bundle integrity and the specified provenance bindings only: it always reports `license_review_required=true`, `release_clearance=false`, and `release_authorized=false`. It does not satisfy the cutover assessor, approve license/privacy/security/name review, or authorize publication. Publish the exact verified candidate files; do not rebuild or recompress them, because any byte change invalidates the source-bound attestations. Release creation and asset attachment remain a separate human-approved operation after every documented parity and cutover gate passes. Existing public-release assets that predate this workflow are not retroactively attested.
