# Release-candidate build process

Threadforge does not publish a GitHub Release automatically. A stable `vMAJOR.MINOR.PATCH` tag starts the release-candidate jobs in `threadforge-tests.yml`, but only after the complete twelve-cell OS/Python test matrix and the Elasticsearch synthetic-ingestion job succeed. The tagged commit must be reachable from `main`. To exercise the release pipeline without creating a tag, manually run the workflow from `main` with `release_version` set to a stable `MAJOR.MINOR.PATCH`; this produces a rehearsal candidate tied to that tested `main` commit, not a tag-sourced production release.

The build creates the currently supported CLI artifacts and requires a separate twelve-cell Python evidence matrix (Linux, Windows, and macOS on Python 3.11, 3.12, 3.13, and 3.14) to succeed before candidate assembly:

- `threadforge_VERSION_linux_amd64.tar.gz`
- `threadforge_VERSION_darwin_amd64.tar.gz`
- `threadforge_VERSION_darwin_arm64.tar.gz`
- `threadforge_VERSION_windows_amd64.zip`
- `threadforge_python-VERSION.tar.gz`
- `threadforge_python-VERSION-py3-none-any.whl`

The version command is linked to the tag version. Each platform archive contains exactly one CLI binary plus the root `LICENSE`, `NOTICE`, `THIRD_PARTY.md`, and the matching target-specific Go license archive as `THIRD_PARTY_LICENSES.tar.gz`. The nested archive contains the bounded `go-licenses` report, evidence manifest, and discovered upstream license/notice texts. Outer archives normalize timestamps, ownership, member names, and metadata where the format permits; the Windows ZIP uses stored entries for byte-stable packaging. The same target-specific `threadforge_VERSION_GOOS_GOARCH.go-licenses.tar.gz` is also retained as a separate, independently attested candidate payload. The Go evidence uses pinned `go-licenses` v2.0.1 for `./cmd/threadforge` under that target's `GOOS`/`GOARCH`; unknown license expressions fail the candidate. The bundle records the source commit, scanner binary hash, notice-file hashes, unknown source-URL count, and native-code inspection warnings. These scanner classifications are unreviewed; the bundle sets `release_clearance=false` and is not legal approval.

The Python source archive and universal wheel are built at the exact candidate version in an isolated staging copy; the checkout's `python/pyproject.toml` version is not rewritten. The sdist retains the Threadforge `LICENSE`, `NOTICE`, and `THIRD_PARTY.md`; both formats include these and the AnyJev/RRSI licenses, credits, and modification notices in `threadforge_py/legal/`, and the wheel carries the project and upstream license files in `.dist-info/licenses/`. The build audits required workspace/Engineering runtime files, rejects model/benchmark binary data, builds the wheel from the source archive, installs it into a temporary target with `--no-deps`, and checks the JSON-over-stdio capabilities operation. Both files receive source-bound provenance attestations and are included in checksums. This validates the distributable module payload and notice retention, not OS/base-image inventory, legal clearance, optional-runtime behavior, or production approval.

The workflow also creates `threadforge_VERSION_python.spdx.json` from the committed `uv.lock` and `pyproject.toml`. It includes every locked package/version record across all seven extras, records dependency edges and lock resolution markers, and binds LF-normalized lock and project-file digests, candidate version, source commit, and extra set. The candidate verifier reconciles both input digests and the package count against all twelve OS/Python evidence profiles and checks their installed packages are represented. Package license fields intentionally remain `NOASSERTION`; this is a lock-derived Python dependency inventory, not license clearance, an OS/base-image SBOM, or proof that every optional backend ran.

The release workflow also runs a separate, non-publishing Engineering image evidence job. It builds the pinned `linux/amd64` image from `containers/engineering/build.ps1`, scans that exact image with Syft, and binds the exported Docker archive, SPDX package inventory, base-image digest, lockfiles, Dockerfile, and source identity. After creating provenance and archive-to-SPDX attestations, it runs `scripts/verify_engineering_runtime_sbom.py` against the bundle. The bundle is retained as a separate 14-day Actions artifact; it is deliberately not included in the 27 public-candidate payloads and does not authorize publishing the container. License fields remain unreviewed and `release_clearance=false`; the hosted build and image SBOM must be reviewed before distribution.

For Python, the workflow installs all seven locked extras declared in `python/pyproject.toml` (`test`, `decisions`, `hf`, `serving`, `typed-data`, `evolution`, and `workspace`) on each of twelve OS/Python profiles and runs the complete Python suite with those extras enabled, then emits one `threadforge_VERSION_python_OS_pyPYTHON.license-evidence.tar.gz` archive per profile. New archives use `threadforge.python-license-evidence.v2`, which binds LF-normalized `uv.lock` and project-file hashes; v1 remains available for older raw-byte hashes. The archive records installed package metadata and safe license fields, and retains bounded license/notice files with per-file hashes. Collector-source and v2 input-manifest SHA-256 values normalize CRLF to LF so identical committed content hashes consistently across Windows and Unix checkouts. Installed packages not represented in `uv.lock`, unsafe paths, and oversized evidence fail the job. The archives are deterministic and individually provenance-attested. They remain unreviewed evidence (`release_clearance=false`), and do not cover the Engineering container/runtime or benchmark dataset/evaluator terms. See the [license audit](license-audit.md) for remaining scope and legal-review gaps.

If Syft installation or the first Go SBOM generation attempt fails, the pinned action is retried once; a second failure stops the candidate before attestation or upload. GitHub creates build-provenance attestations for each archive, SBOM, Go/Python license-evidence bundle, and the two Python distribution files; a distinct SPDX SBOM attestation binds each CLI archive to its SBOM, and a build-provenance attestation binds the combined `checksums.txt`. Candidate assembly requires exactly 27 versioned payloads (4 CLI archives, 4 CLI SPDX SBOMs, 1 Python dependency SPDX SBOM, 4 Go evidence archives, 12 Python evidence archives, and 2 Python distribution files), plus 28 SLSA attestations including `checksums.txt`; the four archive-to-SPDX attestations bind the CLI archives. Python component licenses remain unreviewed and the lock SBOM does not include operating-system/base-image components. License, dependency, and legal review remain explicit release blockers. All payloads are checksummed in the combined candidate bundle. The workflow uploads these files as a 14-day Actions artifact and has no `contents: write` permission, so it cannot publish or edit a public release.

Before attestation, `scripts/verify_release_sbom.py` reconciles each SPDX package set to that exact binary's `go version -m` output. It requires every embedded Go module, checks non-replaced module versions and the Go standard-library version, and rejects unexplained SBOM packages. Its JSON summary counts package license declarations/conclusions that remain unasserted and always sets `license_review_required=true` and `release_clearance=false`. This verifies Go-binary component coverage only; it does not classify licenses, review redistribution terms, cover Python/container runtime dependencies, or grant legal approval. Those release blockers remain tracked in [the dependency and license audit](license-audit.md).

After downloading the candidate artifact, verify the complete bundle with the repository verifier. It checks the exact 27-payload inventory, all payload checksums, archive member safety/layout, Python distribution version/content/notices, the lock-derived Python SPDX package/dependency graph against all twelve evidence profiles, embedded-versus-separate Go license evidence, Go/Python evidence manifest bindings, 28 SLSA provenance attestations, and four archive-to-SPDX attestations. GitHub CLI must be authenticated and able to read the repository's attestations. Use the exact source commit and full ref recorded by the candidate workflow:

```bash
python scripts/verify_release_candidate.py \
  --bundle-dir ./threadforge-candidate \
  --version VERSION \
  --source-commit FULL_SOURCE_COMMIT_SHA \
  --source-ref refs/tags/vVERSION
```

For a `workflow_dispatch` rehearsal from the `main` branch, pass `--source-ref refs/heads/main`; for a tag-triggered candidate, pass its exact `refs/tags/vVERSION` ref. The verifier performs GitHub API lookups for each attestation and may take several minutes. Its success output proves bundle integrity and the specified provenance bindings only: it always reports `license_review_required=true`, `release_clearance=false`, and `release_authorized=false`. It does not satisfy the cutover assessor, approve license/privacy/security/name review, or authorize publication. Publish the exact verified candidate files; do not rebuild or recompress them, because any byte change invalidates the source-bound attestations. Release creation and asset attachment remain a separate human-approved operation after every documented parity and cutover gate passes. Existing public-release assets that predate this workflow are not retroactively attested.

After an authorized tag-based publication, run the read-only post-publication audit against the same downloaded candidate bundle:

```bash
python scripts/verify_published_release.py --bundle-dir ./threadforge-candidate --version VERSION --source-commit FULL_SOURCE_COMMIT_SHA
```

This reruns the complete candidate provenance verifier, confirms the public tag resolves to that exact source commit, and downloads the release assets to compare the exact 27-payload-plus-checksum inventory and every byte. GitHub CLI must be authenticated for release metadata, assets, and attestations. The audit is read-only and always reports `release_clearance=false` and `release_authorized=false`; it cannot publish, repair, delete, or approve a release. A failed comparison requires an operator to investigate and follow the separately approved correction procedure.

Download the Engineering runtime artifact separately to verify its image archive, SPDX schema and package count, source/input hashes, checksums, and five GitHub attestations:

```bash
python scripts/verify_engineering_runtime_sbom.py \
  --bundle-dir ./threadforge-engineering-runtime \
  --version VERSION \
  --source-commit FULL_SOURCE_COMMIT_SHA \
  --source-ref refs/tags/vVERSION
```

For a `main` rehearsal, use `--source-ref refs/heads/main`. This verifier requires authenticated GitHub CLI access to attestations and always reports `release_clearance=false` and `release_authorized=false`. `--skip-attestation-checks` is only for the workflow's structural check before attestations are created; its output expressly records that attestation checks were skipped and is not release verification.

The companion `.github/workflows/threadforge-published-release-verification.yml` runs this audit on stable `release.published` events and can also be started manually with a version. It locates the newest successful `threadforge-tests.yml` push run whose tag name and source commit exactly match the release, then downloads that run's `threadforge-release-candidate-VERSION` artifact as the full candidate bundle. The verifier independently downloads the public assets and compares them only after the full candidate passes provenance checks. The workflow token is limited to `contents: read`, `attestations: read`, and `actions: read`; it fails closed if the exact run or its 14-day artifact is unavailable. A mismatch fails the verification job but cannot prevent a human from publishing or repair the release. This workflow is detection after publication, not a publication or cutover gate.
