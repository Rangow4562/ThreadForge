# Local threat-rule scan

## Dependency vulnerability gate

The cross-platform GitHub workflow also runs `govulncheck` v1.9.0 against the Go packages and `npm audit --audit-level=moderate` against both checked-in npm lockfiles after installation. The Go build toolchain is pinned by `go.mod`; these checks block on known moderate-or-higher advisories in the locked dependency graphs and reachable Go code. They do not replace code review, runtime penetration testing, license review, privacy review, or the all-or-nothing cutover assessment. The npm audit includes development dependencies because the build, test, and packaging toolchain executes in CI.

The GitHub repository requires workflow actions to be pinned to full commit SHAs. External actions in `.github/workflows/` use immutable SHA references; the repository's own CI composite action uses GitHub's `$/.github/actions/...` self-reference so it resolves to the workflow's exact commit. Workflow token permissions are read-only unless an individual job documents a narrower need. This controls action drift, but does not replace reviewing action updates or protecting the default branch with required checks.

`threadforge security scan` runs the vendored, MIT-licensed Beacon threat-rule engine against a local canonical event JSONL file. It is read-only and never makes a network call or executes a rule action. The default corpus is the small frozen baseline embedded by the upstream rule-store package. Additional installed rules default to `<THREADFORGE_HOME>/rules`; `--rules-dir` selects an explicit external corpus and replaces the active corpus for that scan.

Manage the local active corpus with `threadforge security rules list`, `security rules install --source <rule-file|directory> [--force]`, and `security rules remove --id <rule-id>`. Installation snapshots bounded source files, rejects symbolic links and credential-bearing rule content, and validates every rule and its fixtures before any rule is installed. Replacement is explicit with `--force`. Installed rules form the active corpus instead of being merged with the embedded baseline; removing the last installed rule returns scans to the baseline.

The full pinned Beacon corpus is available as an explicit offline pack: `threadforge security rules install --builtin beacon-threat-rules-v1`. It installs 75 rules (215,435 source bytes) from the MIT-licensed Beacon corpus at commit `5303224c63ddb73b7c2a125278f4233d807348d9`. The CLI verifies the pinned rule-set SHA-256 before staging, then validates every rule and embedded fixture and uses the same atomic rule-store installer. The small baseline remains the default until this command is run. The pack includes only fixed upstream test fixtures with credential-shaped examples; its exact content is pinned, while file/directory sources continue to receive the normal credential scan.

Example:

```powershell
threadforge security scan --traces <events.jsonl> --min-severity medium --fail-on high
threadforge security scan --traces <events.jsonl> --session claude-session-123
```

The result lists active rule metadata and privacy-minimized findings. It does not return event bodies, prompts, commands, paths, raw attributes, or user identities. Findings include event timestamps/harness/actions and a truncated event ID when safe; session IDs are replaced with a one-way short fingerprint. This is still local security output and should be handled as sensitive telemetry.

The loopback `GET /v1/security/scan` endpoint and dashboard button run an explicit scan. Responses contain only aggregate finding counts by default. A same-origin request may opt in with `include_findings=true`; it receives at most 100 finding summaries, each with at most 20 timestamp/harness/action references. `min_severity` and an optional `session` substring can narrow the scan; session IDs, event bodies, prompts, commands, paths, and raw attributes are omitted from the response. The dashboard details checkbox is unchecked by default, and the scan runs only after **Run local scan** is pressed. Persistent review history loads only when requested, in 100-item pages; the API caps pages at 200. Only a complete, unfiltered POST scan reconciles global review state. Filtered POST scans remain read-only so findings outside the selected session/severity scope are not incorrectly marked inactive. The CLI JSON result remains the local full-detail interface.

Scanning is bounded to 128 MiB of input, 100,000 valid events, 64 KiB per JSONL record, 500 external rules, 1 MiB per rule, and 64 MiB per rule corpus. `--session <substring>` scopes rule evaluation to events whose session ID contains the supplied value, case-insensitively; the filter is capped at 256 UTF-8 bytes and is not echoed or stored. Malformed or invalid events produce `complete: false`, no findings, and exit code 2 rather than a misleading clean result. Exit code 3 means a finding met `--fail-on`; exit code 0 means the scan completed without crossing that configured threshold. Invalid paths/rules and scan errors return nonzero. The fail threshold is evaluated against all valid findings in the selected session before `--min-severity` filters the findings included in output, matching Beacon's scan-gate contract.

The loopback service keeps `GET /v1/security/scan` read-only. The dashboard's explicit **Run local scan and record** button uses `POST /v1/security/scan`; only a complete scan reconciles persistent review state. An incomplete scan never marks findings inactive or updates review timestamps. The database stores only a SHA-256 finding fingerprint derived from sanitized rule/evidence metadata, rule ID, severity, status, revision, first/last-seen timestamps, active state, and reviewer identifier. Event IDs, prompts, event bodies, paths, and raw attributes are not stored in the review tables.

Review statuses are `open`, `acknowledged`, `resolved`, and `false_positive`. Dashboard updates and `threadforge security reviews set` use an expected revision, so stale concurrent updates fail instead of silently overwriting. Every status transition is append-only and can be inspected with `GET /v1/security/finding-reviews/{fingerprint}/history` or `threadforge security reviews history`. These review labels are local analyst workflow metadata; they do not authorize agent actions or suppress future scans. A scan persists at most 20,000 distinct findings and the database caps retained fingerprints at 100,000; review lists return pages of at most 200.

This closes the persistent local finding-review and session/severity-filtering dashboard slices, not full Beacon security parity. `threadforge ci gate` and the GitHub composite action's optional `security-fail-on` apply the local severity gate to captured CI logs with aggregate-only output; hosted execution is still unverified. Cloud finding views and customer-specific CI wiring remain incomplete.
